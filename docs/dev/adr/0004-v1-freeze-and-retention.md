# V1 冻结与停维护：只修致命问题，上游 EOL 后保留不删

> 状态：accepted（2026-09-12）。背景调查：`docs/dev/research/v2-stable-contract.md`（OpenCode 2 正式版契约调研）。

## 背景与问题

OpenCode 2 正式版（本机 v2.0.1，2026-09-12 取证）发布后，V1/V2 改用同一个 `opencode` 命令、默认不再并存安装；官方 V2 插件文档把「单入口同时暴露 V1 `server()` 与 V2 `setup()`」定义为过渡形态，并建议在 support window 结束后移除 V1 实现。

本插件现状：v1 支持面 = 共享核心（协议 / 伪装 / 模型管线）之上的 `src/host/v1.ts` 宿主接线与配套测试、文档；V1 上游仍在发版（v1.18.30，2026-09-09）且存在未迁移用户。需要回答：v1 支持面之后的投入与退役政策。

## 决策

- **冻结边界**：v1 专属面（`src/host/v1.ts`、v1 专属测试与文档）停止新特性；只修致命问题——崩溃、认证不可用、伪装 / 会话状态错乱、安全问题。共享核心的改动照常双宿主生效，不计入「维护 v1」。
- **停维护时机**：跟随上游信号。上游 V1 明确停更 / EOL 后，v1 维护（含致命问题修复）全部停止；届时安装指引只剩升级建议。
- **保留不删**：停维护后不主动移除 v1 支持，代码与冻结版安装文档原地保留。是否删除留待未来单独决策。

## Considered Options

- **完全静止（致命问题也不修）**：省下的只是共享核心之上的一层接线成本；v1 用户遇到崩溃 / 认证失效将无路可走，而这类问题会从共享核心改动穿透到宿主层（0.1.1 / 0.1.2 的 v1 日志泄漏系列即先例）。否决。
- **立即或限期删除 v1**：与上游信号脱节——V1 上游一周前仍在发版，存量用户尚在；官方移除建议明确以 support window 结束为前提。否决。
- **永久维护 v1**：与 V2 主线的投入方向相悖；v1 宿主交互问题（TUI 日志、hook 时序）属新特性级工作量，无上限。否决。

## Consequences

- v1 issue 按「致命 / 非致命」分流：非致命问题不修，建议升级 V2；致命问题修复后仅做 v1 复验。
- v1 专属面的改动是发布流程中唯一触发 v1 人工复验的条件；常规发布不再跑 v1 轮（流程换轴随本次收口修订 `docs/dev/release/release-process.md`）。
- 安装指南不承载 v1 安装步骤：V1 用户获一句「已冻结 + 升级推荐」指引，安装步骤指向冻结版本文档的固定链接。
- 术语「V1 冻结」收入 `CONTEXT.md`。
