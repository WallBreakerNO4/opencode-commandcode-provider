## GLM 系列模型缓存命中率不稳定，额度消耗快

**现象**

在同一个编码会话中，各次请求的 input token 是连续增长的（上下文高度重复，理论上应持续命中缓存），但单次请求的价格忽高忽低，波动可达约 5 倍——低价格对应高缓存命中，高价格对应近乎零命中。实测一轮会话的综合缓存命中率仅约 54%，而编码 agent 场景通常需要 90% 以上才能获得合理的消耗水平。结果是使用 GLM 系列模型时，额度消耗明显快于其他模型。

下图为同一会话连续请求的用量记录：input token 从 73k 平滑增长到 89k，单次价格却在 $0.02～$0.12 之间反复跳动：

![GLM 系列同一会话内单次请求价格波动](./assets/glm-cache-fluctuation.png)

**原因**

Command Code 官方 API 侧 GLM 系列模型的缓存行为不稳定：上下文相近的连续请求，缓存时而不命中，导致重复上下文按全价计费。其他系列模型（如 deepseek）未观察到此现象，缓存命中率能持续保持高位。

**受影响模型**

- `z-ai/glm-5.3-flash`
- `zai-org/GLM-5.3`
- `zai-org/GLM-5.2`
- `zai-org/GLM-5.2-Fast`
- `zai-org/GLM-5.1`
- `zai-org/GLM-5`

**变通方案**

对额度敏感的日常使用，建议选用 deepseek 系列模型（如 `deepseek/deepseek-v4-pro`、`deepseek/deepseek-v4-flash`），缓存命中率稳定，额度消耗平缓。

**责任边界**

缓存行为发生在 Command Code 官方 API 的模型侧，插件只负责把请求桥接成 OpenCode 原生格式，无法影响上游的缓存策略。请勿为此问题在本仓库提 issue。

**状态**

未修复 · 上游问题
